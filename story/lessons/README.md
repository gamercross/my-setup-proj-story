# 🎓 무엇을 배웠나

숫자나 기능 목록이 아니라, 만드는 과정 자체에서 얻은 것들이다.

---

## 1. 목적은 한 번에 안 잡힌다 — 증상과 원인을 구분하는 법

"내가 뭐가 진척되는지 감이 안 와서"로 5주 넘게 설계·개발을 했다. 그런데 실제로
필요했던 OKR·주간 플래너 기능을 만들고 나서도 뭔가 허전했다 — 그때 처음으로
"이게 정말 원하던 거였나"를 되물었고, "진척률"은 증상이었지 "지식이 안 쌓이는 것"이
진짜 원인이었다는 걸 알았다. **처음 붙잡은 문장을 의심하는 것도 설계의 일부**라는
걸 배웠다 — 그리고 그 의심을 문서에서 지우지 않고 "표면 증상"으로 남겨 뒀다
(REVERSE_PLAN.md §1-0).

## 2. 1인 개발에서 에이전트 파이프라인은 속도가 아니라 자기검열이다

`/feature` 4역할 파이프라인(planner→developer→supervisor→finisher)을 쓴 이유는
"혼자서 못 내는 속도를 보완"하려는 거였다. 그런데 실제로 겪어 보니 진짜 가치는
속도가 아니라 — supervisor 단계가 실제로 문제를 잡아냈다는 데 있었다(예: 기대정렬
위젯의 dead config, 지식 추세 뷰의 문서 누락). 혼자 일하면 건너뛰기 쉬운
"내가 만든 걸 남처럼 다시 보는" 단계를 강제하는 장치였다.

## 3. 정직한 기록이 오히려 신뢰를 만든다

"약점 공개"(§4-5) 섹션에 로컬 네트워크 노출, CORS 허점, 트리거 없는 불변식 같은
문제를 그대로 적었다. 이걸 숨기지 않고 원인→영향→보완까지 적어 두니, 오히려
"이 프로젝트가 뭘 하고 있는지 스스로 알고 있다"는 신호가 됐다 — 완벽해 보이려는
문서보다 이게 더 설득력 있었다.

## 4. 자동화 도구도 조용한 실패를 일으킬 수 있다

GitHub의 "병합 시 브랜치 자동 삭제" 설정을 켠 뒤, 이미 병합된 브랜치 이름으로
다시 커밋을 푸시하면 그 커밋이 어느 PR에도 연결되지 않은 채 원격에 고아로 남는다는
걸 직접 겪었다(2회). 편의 기능 하나를 켜는 것도 워크플로 전체에 영향을 준다는 걸
배웠고, 이후로는 브랜치를 새로 만들기 전에 origin 상태를 다시 확인하는 습관이 생겼다.

## 5. 자기 자신에게도 프로젝트와 같은 방법론이 필요하다

프로젝트에는 ADR(결정 1개 = 파일 1개)이 있는데, 정작 "나는 지금 뭘 하고 있고
왜 하고 있는지"는 어디에도 기록되지 않았다. 기대정렬 체크인은 그 공백을 메우려는
시도였고 — 프로젝트를 관리하는 방식을, 프로젝트를 만드는 사람 자신에게도 그대로
적용해 보니 "내가 지금 방향을 잃었는지 아닌지"가 훨씬 빨리 보였다.
