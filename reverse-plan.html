01

원초적 고민 — 무엇이 문제였나

문서를 역추론하면 "도구가 흩어져 있다"가 먼저지만, 사용자에게 직접 물으니 발단은 달랐다.

중심 줄기: 경험을 지식으로, 지식을 역량으로

2026-09-14 재정의

진척 가시성은 증상이었지 목적이 아니었다. 진짜 중심 줄기는 사용자가 직접 다시 쓴 문장이다.

"우리의 목적은 진척도를 보는 것이 아닌, 경험들이 모인 지식을 시각화·도식화해서 지식 가치를 올리는 것 — 지식이 모여 역량을 증진시키고 그 방향을 한눈에 보이게 하는 것."

"목적의 근간은 자기계발을 더욱 효과적으로, 경험에 대한 지식을 구체화하고 가치를 형성하는 데 있다."

사용자 진술, 2026-09-14

이 프로젝트가 다루는 대상은 완료율이 아니라 지식이다. 할일·프로젝트·OKR·에이전트 활동·문서는 전부 "무엇을 겪었고 그로부터 무엇을 알게 됐는지"가 흩어지지 않고 쌓이는 그릇이며, 그 축적이 역량으로 이어지는 방향을 한눈에 보여 주는 것이 목적이다. "진척이 안 보인다"는 이 결핍이 가장 먼저 만져진 표면이었을 뿐이다(2026-09-09 인터뷰).

"내가 뭐가 진척되는지 감이 안 와서."

이 감각은 세 영역에서 같이 나타났다 — 지식이 쌓이는 자리가 셋으로 흩어져 있다는 뜻이기도 하다.

  1. 개인 삶·일 전반 — 이번 주에 내가 뭘 겪었고 거기서 뭘 배웠는지.
  2. 공부·강의 진도 — 3개 강의에서 쌓이는 지식이 어디로 가는지.
  3. 이 프로젝트 자체의 개발 진도 — P0–P9 를 지나며 쌓인 결정·경험이 무엇을 남겼는지.

최초 인터뷰, 2026-09-09 (§1-0 이전 판)

그래서 이 프로젝트의 메타 문장은 이렇게 다시 읽는다: "이 저장소의 PROGRESS.md가 프로젝트에 해 주는 일 — 흩어진 작업을 하나의 지식 서사로 엮는 일 — 을, 앱이 사용자 자신의 경험에도 해 준다." OKR·주간 플래너·기대정렬 체크인은 삶에서 쌓이는 지식과 역량의 방향을, 진행 현황·파일 탐색 뷰는 프로젝트 자신이 쌓은 지식(결정·근거·트레이드오프)을 같은 방식으로 보여 준다.

파생 고민 (Q1–Q8)

VISION.md의 최종 그림 — "흩어진 도구를 한 앱으로 통합하고, 매일 아침 AI 에이전트가 우선순위를 정리하는 데스크톱 셸" — 은 아래 불편들에서 나왔다. 사용자 확인 결과 8개 모두 실제 고민과 부합하며, 중심 줄기(경험의 지식화·역량 방향 가시화) 아래로 Q3·Q4·Q5·Q7이 묶인다 — 겉보기는 이전과 같지만 "완료율이 보이는가"가 아니라 "쌓인 지식이 한곳에서 보이는가"로 읽는다.

2-2. 대시보드 OS 전환 — "고정 패널을 왜 버렸나" ADR-0020–0022, DO-1–6

Q6에 대한 답. Dashboard.jsx 한 컴포넌트가 모든 패널을 하드코딩하며 비대해졌고, 사용자별 배치도 불가능했다.

  • 위젯 셸 아키텍처 — react-grid-layout 그리드에 위젯 인스턴스를 배치·이동·리사이즈. 새 기능 = widgets/registry.js에 항목 추가(플러그인 유사). 0020
  • 레이아웃 영속화 — localStorage(300ms 디바운스) → SQLite → 사용자별. 0021
  • 위젯별 테마 — 스코프된 CSS 커스텀 프로퍼티(--w-*) + 화이트리스트 config. 외부 코드 실행 없음. 0022
  • 착수 전 6개 질문(DO-1–6): 그리드 스냅 · 타입당 1인스턴스 · localStorage 1차 · config 검증은 프론트만 · 편집 토글 필요 · 다이어그램도 위젯화.

강의 A 정합도 근거였다 — 과목명이 "AI 컴퓨터 운영체제 실습"이고, 위젯 셸은 미니 윈도우 매니저(창 생명주기·z-order·포커스·레이아웃 영속화)의 실습 대상이 된다.

결정 서사 — Q6와 강의의 관계 · 솔직한 기록

§1에서 개인화(Q6)는 "필요조건이지 목적이 아니다"라 적었다. 그런데 위젯 셸은 프로젝트에서 가장 큰 코드 덩어리 중 하나다(C5·C6·P4.5). 왜 목적도 아닌 것에 그만큼 썼나 — 강의 A 때문이다. 커리큘럼에 창·프로세스·포커스·레이아웃 관리가 들어 있고, 고정 대시보드로는 그 주제를 실습 산출물로 보여 줄 수 없었다. 즉 위젯 셸은 제품 필요와 강의 필요가 겹친 지점이라 크게 투자했다 — 커스터마이즈가 갈망 목록에 없다는 사실(§1)은 이 투자가 제품 관점에선 과했을 수 있음을 인정하는 신호이며, §5-2 재검토 노트로 이어진다. 반대로 라이트 테마·OKR 모델·마크다운 렌더는 오래 고민하지 않았다. 유일하게 며칠 붙잡은 건 아래 PO-3이다.

결정 서사 — PO-3: 자유 태그 vs 고정 카테고리

ADR 표에서는 한 줄이지만, 실제로 가장 오래 붙잡은 갈림길이다. 표면 질문은 "분류 체계를 고정 집합으로 둘까, 자유 태그로 둘까"였지만, 사용자를 실제로 멈춰 세운 건 그 아래의 불안이었다.

"에이전트가 내가 달아 둔 태그를 침범하면 어쩌지."

일일 브리핑 배치가 태그 없는 할 일을 Claude로 자동 분류하는데(PO-4), 이 배치가 사용자가 손으로 붙인 태그를 덮어쓰거나 지울 가능성이 걱정이었다. 자동화가 사용자의 의도를 조용히 훼손하는 건, 이 프로젝트가 피하려는 바로 그 패턴이다.

4-1~4-4는 지금 구조를 있는 그대로 그렸다. 이 절은 그 구조가 아직 감당하지 못하는 지점을 원인 → 영향 → 설계 보완 순으로 되짚는다. 공통 원인은 하나다: 로컬 단일 사용자 · 1인 개발 · 마감(C-1·C-2) 가정 아래 "지금은 안 해도 되는 것"으로 미룬 것들이며, 다중 사용자(Phase E)·패키징 배포로 가면 되짚어야 한다. 이 절은 4-1~4-4 스냅샷에 대한 주석이고, 실행 항목은 §6이 추적한다. 2026-09-10 코드 리뷰 시점 판단.

대조군 — 잘 막힌 곳

외부에 노출되는 유일한 "경로를 받는" 표면인 파일 트리·문서 뷰(§5 P9)는 services/{tree,docs}.js에서 심링크 스킵 · 세그먼트별 .. 검사 · route 레이어 재디코드 금지(%252e 우회 차단) · realpathSync 루트 이탈 재확인 · 깊이·항목·1MB 상한으로 다층 방어한다. 같은 마감 압박 아래에서도 여기는 미루지 않았다.

보안 · 안전성

S1 백엔드가 로컬 네트워크에 열려 있다

원인
로컬 HTTP REST(0004) + 인증 미도입은 로컬 단일 사용자 가정(0015) 아래 의도한 결정. 다만 server.js의 app.listen(PORT, cb)가 host 인자 없이 전 인터페이스(0.0.0.0) 바인딩되는 건 Express 기본값을 그냥 둔 것이고, 되짚은 적 없다.
영향
같은 머신의 다른 프로세스뿐 아니라 같은 Wi-Fi의 다른 기기가 :3000/api로 전체 데이터를 읽고 쓸 수 있다.
설계 보완
app.listen(PORT, '127.0.0.1')로 루프백 고정. 패키징 토폴로지에서 ADR-0016 2항으로 못박는다.

S2 CORS가 Origin: null을 모든 빌드에서 허용한다

원인
패키징된 Electron이 file://에서 렌더러를 로드해(데스크톱 프로세스 토폴로지, 0016 영역) fetch가 Origin: null을 보낸다. 이 예외를 middleware/cors.js에 환경 분기 없이 넣어서, 웹 데모(0026)·개발 빌드까지 그대로 상속했다.
영향
브라우저에서 열린 샌드박스 iframe·로컬 HTML 파일도 동일한 Access-Control-Allow-Origin을 받는다.
설계 보완
null 허용을 prod 패키지 빌드로 한정하는 환경 분기.

S3 에이전트의 사용자 태그 비침범이 트리거가 아닌 코드로만 지켜진다

원인
PO-3(0029, §2-3 서사)에서 결정. source 값은 스키마 CHECK로 강제되지만, "이미 사용자 태그가 붙은 할 일에는 에이전트가 손대지 않는다"는 행 단위 불변식은 최소 마이그레이션 전략(0018)이 트리거를 피하는 방향이라 애플리케이션 층에 남았다.
영향
add_agent_tags(태그 0개인 할 일만) + classify.py(환각 id 방어) + get_untagged_tasks(NOT EXISTS)의 3중 가드가 뚫리거나 새 쓰기 경로가 생기면, §2-3이 우려하던 상황이 다시 열린다.
설계 보완
"이미 source='user' 태그가 있으면 source='agent' INSERT를 무시" 트리거를 마이그레이션으로 추가. 침범 시도 회귀 테스트를 agent 스위트에 고정.

S4 OAuth 토큰 암호화 키에 회전 절차가 없다

원인
비용 0 목표(C-4) 아래 토큰을 Fernet 대칭키 1개로 암호화한 파일에 뒀다(0024). 키 회전·유출 대응은 학습·발표 산출물 범위(C-5)에서 빠졌다.
영향
TOKEN_ENCRYPTION_KEY 하나가 유출되면 Gmail·Calendar 읽기 토큰 전부가 풀린다.
설계 보완
키 회전 런북, 유출 시 재인증 경로 문서화. (토큰 파일 권한 0600은 이미 google_oauth.py에서 chmod로 설정 중 — 회전만 남았다.)

S5 시크릿 커밋 방지가 .gitignore 한 겹뿐이다

원인
공개 저장소라 시크릿·개인정보 커밋 금지(C-6)인데, 실제 방어는 .gitignore와 브랜치 가드 훅뿐이다. 훅은 main 편집을 막는 용도지 시크릿 스캐너가 아니다.
영향
.env는 무시되지만, 패턴에서 벗어난 새 시크릿 파일은 그대로 커밋될 수 있다.
설계 보완
pre-commit 시크릿 스캔(gitleaks 등) 훅 추가.

5-2. 재검토 노트

역 계획서라면 "만들었지만 다시 볼 것"도 남긴다. 지금 시점의 판단이며, 바뀌면 갱신한다.

기능판단근거 · 함의
위젯별 테마·표시 옵션 (C6) 유지 · 우선순위 낮음 사용자 진술: "유지는 되되 우선순위가 낮다." 방향이 틀린 건 아니다 — 인프라(themeToVars 화이트리스트·configSchema 자동 폼·프리셋)는 재사용되고, 표시 옵션(정렬·완료 숨김)은 실제로 쓰인다. 다만 위젯별 색·모서리 커스터마이즈는 갈망 목록에 없었다(§1). 앞으로 다듬기 시간을 여기 더 쓰지 않는다 — 전역 테마 1벌(라이트/다크)로 충분. 새 위젯을 낼 때 theme 탭 확장에 시간 쓰지 말 것.

이 노트가 커지면 별도 RETROSPECTIVE.md로 분리한다.
